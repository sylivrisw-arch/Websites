Building style

How I make it

Every step below comes from files in the project folder: the numbered backups, the audit lists, the notes and the launcher. Where a step has words to say to the AI, those are suggestions in the same spirit, not quotes. Follow the steps in order and you will make something the way these projects were made.

The recipe in one go

  • 01Pick a target: one picture and one sentence.
  • 02Start one file, with a settings block and a launcher.
  • 03Ask for the smallest version that does the sentence.
  • 04Run it yourself. Send back the whole error, or what you saw.
  • 05When it works, save a numbered copy named for what it does.
  • 06Change one thing. The change that makes the others easier goes first.
  • 07Ask what was not tested, and test that part yourself.
  • 08Every few features, ask for a list of problems with IDs, and check each one.
  • 09Fix by ID, then save the next numbered copy.
  • 10When the file gets big, write the map, the confidence tags and the limits.

Part 1

Set up the ground

Do this once, before the first feature.

Lesson 01

One file you can open

Each big project lives in one file. The game is about 6,900 lines, the physics engine about 10,900, and the main app about 31,000. Even the app's two helper programs sit inside it as text and start from memory. There is nothing to link up and nothing to lose, and the whole thing can be copied, backed up or handed to an AI in one go.

From the folder

voidcraft.py, physics_engine.py and VoidLoader-new.py. The physics engine's own header describes itself as "one file".

Say this

"Write this as one Python file. No other files, and no folders of helpers."

Good to know

A file this big needs a map, or you will get lost in it. That is lesson 13.

Lesson 02

Put every number you might change in one block

The first lines of the file are a block of settings. Each line says what it does and what range makes sense, so you can change the feel of the game without reading any code.

# ═══════════════════════════════════════════════
#  >>>  EDIT YOUR SETTINGS HERE  <<<
# ═══════════════════════════════════════════════
TARGET_FPS        = 60
RENDER_DIST       = 15
STORM_STRENGTH    = 0.85      # 0..1: how far the sky is pulled to storm grey
HARDNESS_SCALE   = 1.0       # multiplies every block's hit points (2.0 = twice as tough, 0.5 = softer)
From the folder

These lines are from the top of voidcraft.py.

Say this

"Put every number I might want to change into one settings block at the top. Give each a comment with what it does and its sensible range."

Good to know

A setting with no range in its comment is a guess waiting to happen.

Lesson 03

Write a launcher that keeps the error on screen

The game starts from a small launcher file. It picks the Python launcher if there is one, installs the graphics package once if it is missing, and runs the game. The last four lines matter most: if the game exits with an error, the window stays open, so you can copy the message and send it back.

@echo off
cd /d "%~dp0"
title Voidcraft
set PY=python
where py >nul 2>nul && set PY=py
%PY% -c "import wgpu" >nul 2>nul
if errorlevel 1 (
    echo Installing the Vulkan renderer ^(wgpu^), one time only...
    %PY% -m pip install wgpu
)
%PY% voidcraft.py %*
if errorlevel 1 (
    echo.
    echo Voidcraft exited with an error. See the message above.
    pause
)
From the folder

This is run_voidcraft.bat, saved next to the game file in every backup.

Say this

"Write a .bat launcher for tool.py. Use py if it exists, install anything missing once and say so, run the file, and pause only if it exits with an error."

Good to know

Without the pause, a crash closes the window and the error is lost.

Part 2

Make one feature, start to finish

The same six steps for every feature, big or small.

Lesson 04

Pick a target: a picture and a sentence

Before any code, get a picture of what you want and write one sentence for the first milestone. For the game's destruction, the picture shows a stone tower snapping at its base and leaning over, with dust, loose blocks and a dug-out hole in the ground. The sentence is one pillar that stands, tips when its base is dug out, and falls as one solid piece.

From the folder

VoidCraft Voxel Pillar Collapse.png, titled "VOIDCRAFT - DESTRUCTION CONCEPT" in its corner. Its file time is about 24 minutes before backup 9, the copy that adds structures and rigid bodies.

Say this

"Here is the picture. First milestone: one pillar that stands, tips over when I dig out its base, and falls as one solid piece. Nothing else yet."

Good to know

Say what is not in this milestone. It keeps the AI from adding things you did not ask for.

Lesson 05

Ask for the smallest version

Ask for one change to the file you already have, and ask where it goes before it is written. Small changes are easy to check. Look at how small the steps in the real project were: backup 3 added one thing, a debris system, and backup 7 added one function.

From the folder

Backup 3 adds the class DebrisSystem. Backup 7 adds the function _separate. Nothing else is new in either.

Say this

"Give me the smallest version of this as one change to my current file. Show me where it goes first, and do not touch anything else."

Good to know

If the AI sends back the whole file, check the line count against yours. A big drop means something was lost.

Lesson 06

Run it yourself, and send back everything

The AI cannot run the game on your machine, so you are the tester. Save the file, double-click the launcher, and try the new thing. If it breaks, copy the whole error from the window that stayed open. If it runs but looks wrong, say what you expected and what you saw.

Say this

"I ran it with the .bat. I expected the pillar to tip when I dug under it. It stayed standing. Here is the full console output: (paste all of it)."

Good to know

Paste the whole message, not just the last line. The cause is often a few lines up.

Lesson 07

Save a numbered copy when it works

As soon as a feature works, copy the file with a number before you change anything else. The game folder holds eleven numbered copies plus the current file. Put them side by side and you can see the whole build, one working step at a time.

Have a go

When a feature works, copy the file as name-backupN-feature.py before you touch it again.

Good to know

Only one of these copies has the feature in its name. Name them all and you will never open three to find the right one.

Lesson 08

Change one thing, and do the enabling change first

Before a run of changes, ask for them in order. A saved plan for the game's graphics lists six upgrades. The first is not the flashiest: it changes how lighting is stored so that everything after it gets easier. The plan says nothing should look different afterwards, and to check that before moving on. The same plan lists what to skip, and asks whether the game should stay blocky but well lit or chase photo realism.

From the notes

"Everything below depends on this, so check it matches the current look before moving on."

Say this

"List the changes I want in the order that makes each one easier. Say which goes first and why, what should look identical afterwards, and what we are not doing."

Good to know

A change that should look identical is a good test. If it looks different, something broke.

Lesson 09

Ask what was not tested

At the end of a session, ask for an "unfinished" note: what the AI could not check, and how to check it on your own machine. The game folder has one. It says the tests ran on Linux, that the Windows build starts its workers differently, and what to run to confirm it.

From the folder

notes/notes.txt opens with "### unfinished ###". One line reads: "My tests ran on Linux... Run the game as a script once, then the .exe if you use one, and confirm the first mesh loads without a stall."

Say this

"Before we stop, write a short 'unfinished' note: what you could not test here, and exactly how I can check each thing on my machine."

Good to know

Keep the note in a notes folder beside the backups. Do the checks at the start of the next session.

Part 3

Check it

Every few features, stop adding and look for what is wrong.

Lesson 10

Ask for a list of problems with IDs

Ask the AI to read the whole file and list what is wrong, in groups, each with an ID. The game folder has one with 19 findings: P1 to P7 for performance, R1 to R6 for rendering, D1 to D6 for physics. Each has the function it lives in, what happens, and a one-line fix. Then you can say "fix P3 and P4" and nothing else.

From the folder

buggy/Verified findings.txt. P3 reads: a blur is computed, then its result is replaced by a flat array of ones, so the work is wasted. Fix: "Either restore the AO calculation or remove the blur."

Say this

"Read the whole file. List problems under Performance, Rendering and Physics. Give each an ID (P1, R1, D1), the function it is in, what happens, and a one-line fix. Only list what you can see in the code."

Good to know

Fix a few IDs at a time, then run it and save the next numbered copy.

Lesson 11

Check the list before you trust it

A list of problems is itself a claim. In the findings file, D6 is headed "not a defect in this file": an earlier review said an explosion light never fades, but in this file it does. For the main app, a second pass checked all sixteen findings of a first review. It said some were too absolute, and that two rated green could affect how the app works.

From the folder

VoidLoader_Audit_Verification.txt: "Real vulnerability; 'any website' needs qualification."

Say this

"Here is another review of the same file. For each finding say confirmed, overstated or wrong, and point to the line that shows it."

Good to know

A second AI is only a second guesser. Wherever you can, check by running the thing.

Lesson 12

A claim is not a fact

One small project exists only to prove this. The AI may claim and propose, but only the program records what really happened, and "verified" is worked out from the records, never written down. A deliberately dishonest test agent made sixteen claims, and only two survived with evidence behind them.

From the README

"There is no field a model could set to verified."

Say this

"Of the things you just told me, which did you run and see, and which did you only read in the code?"

Good to know

A test the AI wrote itself is not independent proof. The project labels it "passed, not independent".

Part 4

Write it down

When a file gets big, notes keep you in control of it.

Lesson 13

Get a map written beside the file

The 31,000-line app has a code map: a table of line ranges and what each layer does, then three edit zones. Safe is things like constants and themes. Careful is pages that are rebuilt often. Fragile is the tab system and startup order. It also lists functions called by name from text, so a normal search will not find them.

From the map

"Renaming a Settings tab title silently breaks its set_* method." A fact like that is easy to forget and costly to find again.

Say this

"Read the whole file. Write a code map: a table of line ranges and what each layer does, then Safe, Careful and Fragile edit zones, and anything called by a built string that a search would miss. Say what you did not check."

Good to know

A map goes stale. Ask for it again after big changes, and put what changed at the top.

Lesson 14

Tag how sure each note is, and write the limits

The long knowledge file opens by saying everything came from reading the code, and nothing was run. Statements carry tags: [CODE] means it is visible in the source, [UNTESTED] means it looks like it could misbehave but needs a real run, and [YOUR NOTE] means you reported it. The trust project ends with a Limits section that says plainly what it cannot do.

From the notes

"HOW MUCH TO TRUST THIS: everything comes from READING the code. Nothing was run."

Say this

"Tag every statement: [CODE] if you can see it in the source, [RAN] if you ran it and saw it, [UNTESTED] if it is a guess. End with a Limits section."

Good to know

A limit you wrote yourself is a favour to the next person. A limit someone else finds is a bug report.

Part 5

Own the parts

What to build from scratch, and how to keep it safe.

Lesson 15

Build the part that makes it yours, and keep a way back

The big projects carry their own engines: a model loader of 1,312 lines, a physics engine that runs on the graphics card, and a Vulkan renderer. The payoff is that you understand every part and it all works offline. Each has a way back. The tools run on the processor if the graphics-card package is missing, and the older graphics path stays as a basic fallback. Heavy parts run as their own program: the physics menu starts the engine separately and reads its formula list from the file's text without running it.

From the folder

USE_GPU = True with the comment "use the NVIDIA GPU if CuPy is installed, otherwise the CPU". physics_menu.py is under 8 KB. The engine it launches is over 500 KB.

Say this

"Add the fast path, but keep the plain one. If the fast one fails to start, fall back and tell me why in one line."

Good to know

Building your own engine costs a lot of time. Do it only for the parts that make the project yours.

Build your own

Make a working tool

In eight steps you will make a small tool that runs in your browser, save it, and add one improvement. This page is an activity: you finish with something that works. Plan on an hour or so.

What you need

  • 01A free AI chat assistant. Any one will do.
  • 02A plain text editor: Notepad on Windows, or TextEdit on a Mac.
  • 03A web browser, such as Chrome, Edge, Firefox or Safari.
Before you start

Every tool on this page is a single HTML file that runs in your browser. No Python or other programming tools yet, and nothing to install.

At the end you will have a tool you can open any time, a saved copy of the first working version, and one improvement on top. This is the same loop described in How I make it, at a size you can finish in one sitting.

Part 1

Plan it

Two short steps before you touch the AI.

Step 01

Pick something small

Choose something you would enjoy using, and keep it small. Pick one below, or choose your own idea.

Good to know

If you cannot describe it in a sentence, the idea is still too big. Cut it down to the first thing it must do.

Step 02

Describe the first working version

Write a few plain sentences covering three things: what you will type or click, what should appear on the screen, and how you will know it works. We have filled in an example for your pick. Change it until it sounds like what you want.

Good to know

Describe only the first version. You will add the extras one at a time in step 8.

Part 2

Build the first version

Get a file on your computer, ask for the code, and run it.

Step 03

Get ready to run it

Your tool will be a single HTML file, which is a web page saved as a file. It is not Python or any other kind of program. It runs in your browser, so there is nothing to install. Set up a home for it now, so the code has somewhere to go.

Set up
  1. Make a folder on your desktop called my first tool.
  2. Windows: open Notepad. Mac: open TextEdit, then open the Format menu and choose Make Plain Text.
  3. When you have the code (step 4), paste it into the empty file and save it in your folder as tool.html.
  4. Windows only: in the Save window, set "Save as type" to All files. Otherwise Windows saves it as tool.html.txt and it will not open as a page.
  5. To run it, double-click tool.html. It opens in your browser.
Good to know

When you change the file later, save it and press F5 in the browser (Cmd+R on a Mac) to see the new version. Do not type passwords or private details into your tool or the chat.

Ask the AI to build it
